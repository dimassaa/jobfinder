 Моя тема - Приложение для учёта обращений в службу занятости с модулем анализа вакансий

Общие требования. Программное средство должно быть реализовано в архитектуре клиент–сервер с поддержкой многопоточной обработки запросов, обеспечивающей высокую производительность и масштабируемость. Взаимодействие с реляционной базой данных должно быть организовано на объектно‑ориентированном языке Java (версия 21) с использованием современных библиотек и фреймворков.

_Архитектурные уровни_.

Серверное приложение может быть реализовано в виде консольного или GUI‑решения, при этом конфигурация параметров должна осуществляться без изменения исходного кода (через аргументы командной строки, конфигурационные файлы, переменные окружения).

Клиентское приложение должно быть реализовано как оконное приложение с использованием библиотек пользовательского интерфейса (JavaFX, Swing, AWT), поддерживающих событийную модель и асинхронный обмен данными.

Взаимодействие между клиентом и сервером должно быть организовано на основе протокола TCP/IP с использованием сокетов. Передача данных должна обеспечивать: корректную сериализацию и десериализацию объектов (например, через встроенные механизмы Java или форматы JSON/XML/Protocol Buffers); поддержку многопоточной обработки запросов на серверной стороне; синхронизацию состояния при параллельном доступе к общим ресурсам; контроль целостности и корректности получаемых данных; обработку ошибок сетевого взаимодействия и восстановление соединения после разрыва.

_Требования к реализации._

1 Разработка и использование собственной иерархии классов (не менее 5), включая применение принципов SOLID и расширение базовых классов JDK.

2 Реализация не менее двух паттернов проектирования (например, Singleton, Factory Method, Observer, Strategy, Builder).

3 Использование объектно‑ориентированных механизмов: инкапсуляция, перегрузка и переопределение методов, сериализация, абстрактные типы данных (интерфейсы, абстрактные классы), статические методы, обработка исключительных ситуаций, применение generics и лямбда‑выражений.

4 Внедрение модульного тестирования (JUnit, Mockito) для проверки корректности бизнес‑логики.

5 Использование системы сборки (Maven/Gradle) и средств управления зависимостями.

_Бизнес-логика_. Должна быть реализована исключительно на серверной стороне приложения, с поддержкой параллельной обработки запросов посредством пула потоков или асинхронных API. Функциональные возможности серверной части должны включать не менее 12 высокоуровневых вариантов использования, выходящих за рамки тривиальных CRUD‑операций. Необходимо предусмотреть механизм авторизации и аутентификации пользователей с использованием ролей (например, администратор, сотрудник компании, бухгалтер, менеджер, диспетчер, гость).

_База данных_. 

Проектирование и разработка реляционной модели (не менее 5 связанных таблиц) должно быть выполнено с применением процедуры нормализации до третьей нормальной формы (3НФ). Связи между таблицами должны быть определены как идентифицирующие и неидентифицирующие, с указанием мощности связи. Схема базы данных должна обеспечивать ссылочную целостность данных. Доступ к данным должен осуществляться через JDBC‑драйвер или ORM‑технологии (Hibernate, JPA).

_Технологии_. 

Конкретные версии фреймворков и библиотек должны быть актуальными на начало 2026 года.

3.2. Среда выполнения. Разработанное программное обеспечение должно функционировать в среде Windows 10/11, допускается использование контейнеризации (Docker) и систем виртуализации. Возможна предустановка дополнительных библиотек или пакетов выбранной среды программирования.
