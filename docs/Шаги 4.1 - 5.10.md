## **Этап 4: Управление профилем и тегами (User, HR)**

### **4.1 Создание DTO для профиля и тегов**
- **Что делаем:** Определяем структуры данных для передачи информации о профиле и тегах между клиентом и сервером.
- **Файлы (в модуле `common`):**
  - `ProfileDto.java`
    - Поля: `name`, `surname`, `city`, `phone`, `additionalInfo` (для соискателя).
    - Для HR добавляется `CompanyProfileDto` с полями `companyName`, `website`, `description`.
  - `TagDto.java`
    - Поля: `id`, `name`, `isActive`.
  - `UserTagsUpdateRequest.java`
    - Поля: `List<Integer> tagIds`.
- **Проверка:** Классы компилируются, сериализуются в JSON.

### **4.2 Расширение UserRepository методами для профиля**
- **Что делаем:** Добавляем в `UserRepository` методы обновления полей профиля и получения тегов пользователя.
- **Файл:** `server/repository/UserRepository.java`
  - Метод `void updateProfile(int userId, String name, String surname, String city, String phone, String additionalInfo)` (или через объект `User`).
  - Метод `List<Tag> findUserTags(int userId)` (JOIN с `user_tags` и `tags`).
  - Метод `void updateUserTags(int userId, List<Integer> tagIds)` (удалить старые связи, вставить новые в транзакции).
- **Проверка:** Написать тесты для новых методов в `UserRepositoryTest`.

### **4.3 Создание CompanyRepository для профиля HR**
- **Что делаем:** Реализуем репозиторий для работы с таблицей `companies`.
- **Файл:** `server/repository/CompanyRepository.java`
  - Методы:
    - `Optional<Company> findByUserId(int userId)`
    - `void save(Company company)` (для создания при регистрации HR, если ещё не сделано в Этапе 3)
    - `void update(Company company)`
- **Проверка:** Тест `CompanyRepositoryTest` с сохранением и обновлением.

### **4.4 Создание TagService**
- **Что делаем:** Сервис для работы со справочником тегов.
- **Файл:** `server/service/TagService.java`
  - Зависимость: `TagRepository`.
  - Метод `List<TagDto> getAllActiveTags()` – возвращает список всех активных тегов, преобразованных в DTO.
- **Проверка:** Модульный тест `TagServiceTest` с моком репозитория.

### **4.5 Создание UserService для профиля**
- **Что делаем:** Сервис, объединяющий операции с профилем пользователя и его тегами.
- **Файл:** `server/service/UserService.java`
  - Зависимости: `UserRepository`, `CompanyRepository`, `TagRepository`.
  - Методы:
    - `ProfileDto getProfile(int userId)` – собирает данные пользователя и (если HR) компании.
    - `void updateProfile(int userId, ProfileDto dto)` – обновляет поля пользователя и компании (если HR).
    - `List<TagDto> getUserTags(int userId)`
    - `void updateUserTags(int userId, List<Integer> tagIds)` – валидация, что теги существуют и активны.
- **Проверка:** `UserServiceTest` с замоканными репозиториями.

### **4.6 Реализация серверных обработчиков команд для профиля**
- **Что делаем:** Добавляем команды в `ClientHandler` для обработки запросов профиля.
- **Команды:**
  - `GET_PROFILE` → вызывает `userService.getProfile(userId)` (userId берётся из текущей сессии).
  - `UPDATE_PROFILE` → десериализует `ProfileDto`, вызывает `userService.updateProfile(...)`.
  - `GET_USER_TAGS` → возвращает теги пользователя.
  - `UPDATE_USER_TAGS` → принимает `UserTagsUpdateRequest`, вызывает `userService.updateUserTags(...)`.
  - `GET_ALL_TAGS` → вызывает `tagService.getAllActiveTags()`.
- **Безопасность:** Проверять, что пользователь аутентифицирован и `userId` совпадает с сессией.
- **Проверка:** Через тестовый клиент отправить команды и проверить ответы.

### **4.7 Клиентская модель данных и сервис для профиля**
- **Что делаем:** В клиенте создаём класс для хранения данных текущего пользователя и сервис для взаимодействия с сервером по профилю.
- **Файлы:**
  - `client/model/UserProfile.java` (поля аналогичны DTO).
  - `client/service/ProfileClientService.java` – обёртка над `NetworkService` для отправки команд `GET_PROFILE`, `UPDATE_PROFILE` и т.д.
- **Проверка:** Подключить к реальному серверу (ручной тест).

### **4.8 Создание UI для редактирования профиля (FXML + Controller)**
- **Что делаем:** Верстаем форму профиля с полями: имя, фамилия, город, телефон, дополнительная информация. Для HR добавляем поля компании.
- **Файлы:**
  - `client/src/main/resources/fxml/profile.fxml`
    - `TextField` для имени, фамилии, города, телефона.
    - `TextArea` для доп. информации.
    - Для HR: дополнительная панель с полями названия компании, сайта, описания (видимость по роли).
    - Кнопка «Сохранить».
  - `client/controller/ProfileController.java`
    - При инициализации загружает профиль через `ProfileClientService` и заполняет поля.
    - Обработчик кнопки «Сохранить» собирает данные и отправляет `UPDATE_PROFILE`.
    - Показывает уведомление об успехе/ошибке.
- **Проверка:** Запустить клиент, войти как соискатель/HR, открыть профиль, изменить данные, сохранить, перезайти – изменения сохранились.

### **4.9 Создание UI для управления тегами пользователя**
- **Что делаем:** Добавляем вкладку или диалог для выбора навыков (тегов) из общего списка.
- **Файлы:**
  - `client/src/main/resources/fxml/tags_selector.fxml`
    - `ListView<TagDto>` с множественным выбором (`SelectionMode.MULTIPLE`) для отображения всех доступных тегов.
    - Кнопки «Сохранить», «Отмена».
  - `client/controller/TagsSelectorController.java`
    - При открытии загружает все теги (`GET_ALL_TAGS`) и выбранные теги пользователя (`GET_USER_TAGS`).
    - Подсвечивает уже выбранные.
    - По кнопке «Сохранить» отправляет `UPDATE_USER_TAGS`.
- **Проверка:** Выбрать несколько тегов, сохранить, переоткрыть – выбор сохранился.

### **4.10 Интеграционное тестирование сценария профиля**
- **Что делаем:** Пишем интеграционный тест на сервере, эмулирующий полный цикл работы с профилем.
- **Сценарий:**
  1. Зарегистрировать нового соискателя.
  2. Войти, получить сессию.
  3. Запросить профиль – должен быть пустой/дефолтный.
  4. Обновить профиль (имя, город).
  5. Запросить профиль – проверить изменения.
  6. Получить все теги, обновить теги пользователя (выбрать 2-3).
  7. Получить теги пользователя – проверить.
- **Использовать:** Java-клиент с сокетами в тесте или Testcontainers для поднятия окружения.
- **Проверка:** Все шаги проходят успешно.

## **Этап 5: Вакансии (CRUD, фильтрация, поиск) для HR и просмотр для всех**

### **5.1 Создание DTO для вакансии и фильтров**
- **Что делаем:** Определяем структуры данных для передачи вакансий и параметров поиска.
- **Файлы (в модуле `common`):**
  - `VacancyDto.java`
    - Поля: `id`, `companyId`, `companyName`, `title`, `description`, `city`, `salaryMin`, `salaryMax`, `employmentType`, `isActive`, `createdAt`, `tags` (список `TagDto`).
  - `VacancyCreateRequest.java`
    - Поля: `title`, `description`, `city`, `salaryMin`, `salaryMax`, `employmentType`, `tagIds`.
  - `VacancyFilterDto.java`
    - Поля: `city`, `salaryFrom`, `salaryTo`, `employmentType`, `tagIds`, `keyword` (для поиска в заголовке/описании).
- **Проверка:** Компиляция и сериализация.

### **5.2 Расширение VacancyRepository методами CRUD и поиска**
- **Что делаем:** Дополняем репозиторий методами для создания, обновления, поиска с фильтрацией.
- **Файл:** `server/repository/VacancyRepository.java`
  - Существующие методы: `save`, `findById`, `findAllActive`.
  - Новые методы:
    - `void update(Vacancy vacancy)`
    - `void close(int id)` (установить `is_active = false`, `closed_at = NOW()`)
    - `List<Vacancy> search(VacancyFilterDto filter)` – динамический SQL с JOIN на теги, фильтрация по городу, зарплате, типу занятости, ключевому слову (ILIKE), тегам (если указаны – вакансия должна содержать все указанные теги).
    - `void addTags(int vacancyId, List<Integer> tagIds)`
    - `void clearTags(int vacancyId)`
- **Проверка:** Тесты `VacancyRepositoryTest` для поиска с разными комбинациями фильтров.

### **5.3 Создание VacancyService с бизнес-логикой**
- **Что делаем:** Сервис, инкапсулирующий операции с вакансиями и проверки прав.
- **Файл:** `server/service/VacancyService.java`
  - Зависимости: `VacancyRepository`, `CompanyRepository`, `TagRepository`.
  - Методы:
    - `VacancyDto create(int companyId, VacancyCreateRequest req)` – создаёт вакансию, привязывает теги. Проверяет, что компания принадлежит текущему HR.
    - `void update(int vacancyId, int userId, VacancyCreateRequest req)` – только владелец компании-работодателя.
    - `void close(int vacancyId, int userId)` – только владелец.
    - `VacancyDto getById(int vacancyId)` – возвращает DTO с информацией о компании и тегами.
    - `List<VacancyDto> search(VacancyFilterDto filter)` – вызывает `vacancyRepository.search()` и преобразует в DTO.
    - `List<VacancyDto> getByCompany(int companyId)` – для HR.
- **Проверка:** `VacancyServiceTest` с моками.

### **5.4 Реализация серверных обработчиков команд для вакансий**
- **Что делаем:** Добавляем команды в `ClientHandler` для CRUD вакансий и поиска.
- **Команды:**
  - `CREATE_VACANCY` – принимает `VacancyCreateRequest`, получает `companyId` по `userId` сессии, вызывает `vacancyService.create()`. Доступно только HR.
  - `UPDATE_VACANCY` – аналогично, с проверкой прав.
  - `CLOSE_VACANCY` – принимает `vacancyId`, закрывает.
  - `GET_VACANCY_DETAILS` – принимает `vacancyId`, возвращает `VacancyDto`.
  - `SEARCH_VACANCIES` – принимает `VacancyFilterDto`, возвращает список вакансий. Доступно всем (включая гостей).
  - `GET_MY_VACANCIES` – для HR, возвращает список вакансий его компании.
- **Проверка:** Написать интеграционный тест для `SEARCH_VACANCIES` с разными фильтрами.

### **5.5 Добавление в Vagrant (опционально) / уточнение: Настройка индексов БД для быстрого поиска**
- **Что делаем:** Убедиться, что в `init.sql` созданы необходимые индексы для полей, участвующих в поиске и фильтрации.
- **Индексы:**
  - `vacancies(city)`
  - `vacancies(salary_min, salary_max)`
  - `vacancies(employment_type)`
  - GIN индекс для полнотекстового поиска по `title` и `description` (опционально, для `ILIKE` можно обойтись без него, но для продакшена полезен).
- **Проверка:** Выполнить `EXPLAIN ANALYZE` на поисковом запросе и убедиться, что используются индексы.

### **5.6 Клиентский сервис для работы с вакансиями**
- **Что делаем:** Создаём в клиенте класс-обёртку для отправки команд, связанных с вакансиями.
- **Файл:** `client/service/VacancyClientService.java`
  - Методы: `search(FilterDto)`, `getDetails(int id)`, `create(VacancyCreateRequest)`, `update(...)`, `close(...)`, `getMyVacancies()`.
- **Проверка:** Проверить работоспособность методов через интеграцию с сервером (ручной тест).

    - **`server/repository/VacancyRepository.java`**
        
        - В методе `search(VacancyFilterDto filter)` добавить условие:

    - **`client/controller/VacancyListController.java`**

### **5.10 Интеграционное тестирование сценариев вакансий**
- **Что делаем:** На серверной стороне пишем тест, эмулирующий полный цикл работы с вакансиями.
- **Сценарий:**
  1. Зарегистрировать и войти как HR.
  2. Создать новую вакансию с несколькими тегами.
  3. Получить список своих вакансий – убедиться, что созданная там есть.
  4. Выполнить поиск по ключевому слову/городу – вакансия должна находиться.
  5. Обновить вакансию (изменить зарплату).
  6. Закрыть вакансию – в поиске активных она не должна отображаться.
  7. Гостевым запросом (без сессии) проверить, что закрытая вакансия не видна.
- **Использовать:** Java-клиент в тесте, подключающийся к серверу, запущенному в Testcontainers.
