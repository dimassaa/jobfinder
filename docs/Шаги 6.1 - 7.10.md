## **Этап 6: Отклики, избранное, история просмотров, жалобы**

### **6.1 Создание DTO для откликов, избранного и жалоб**
- **Что делаем:** Определяем структуры данных для обмена информацией между клиентом и сервером.
- **Файлы (в модуле `common`):**
  - `ApplicationDto.java`
    - Поля: `id`, `vacancyId`, `vacancyTitle`, `userId`, `userName`, `status` (PENDING, INVITED, ACCEPTED, REJECTED), `createdAt`, `updatedAt`.
  - `ApplicationStatusUpdateRequest.java`
    - Поля: `applicationId`, `newStatus` (enum или String).
  - `FavoriteRequest.java`
    - Поля: `vacancyId`.
  - `ComplaintCreateRequest.java`
    - Поля: `targetType` (VACANCY, USER), `targetId`, `reason`.
- **Проверка:** Классы компилируются, сериализуются в JSON.

### **6.2 Расширение репозиториев для откликов (ApplicationRepository)**
- **Что делаем:** Дополняем `ApplicationRepository` необходимыми методами.
- **Файл:** `server/repository/ApplicationRepository.java`
  - Существующие методы: `save`, `findByUserId`, `findByVacancyId`.
  - Новые методы:
    - `Optional<Application> findExisting(int userId, int vacancyId)` – проверка на повторный отклик.
    - `List<Application> findByVacancyIdWithUser(int vacancyId)` – JOIN с `users` для получения имени соискателя.
    - `void updateStatus(int applicationId, String status)`
    - `int countByUserLastMinute(int userId)` – для защиты от спама (подозрительная активность).
- **Проверка:** Тесты `ApplicationRepositoryTest` для новых методов.

### **6.3 Создание репозиториев для избранного, истории просмотров и жалоб**
- **Что делаем:** Реализуем недостающие репозитории.
- **Файлы:**
  - `server/repository/FavoriteRepository.java`
    - Методы: `void add(int userId, int vacancyId)`, `void remove(int userId, int vacancyId)`, `List<Vacancy> findFavoritesByUser(int userId)`, `boolean exists(int userId, int vacancyId)`.
  - `server/repository/ViewHistoryRepository.java`
    - Методы: `void add(int userId, int vacancyId)` (INSERT с ON CONFLICT DO NOTHING или обновлением времени), `List<Vacancy> getRecentViews(int userId, int limit)`.
  - `server/repository/ComplaintRepository.java`
    - Методы: `void save(Complaint complaint)`, `List<Complaint> findAllPending()`, `void updateStatus(int id, String status, int resolvedBy)`.
- **Проверка:** Модульные тесты для каждого репозитория.

### **6.4 Создание ApplicationService с бизнес-логикой откликов**
- **Что делаем:** Сервис, обрабатывающий создание откликов и управление статусами.
- **Файл:** `server/service/ApplicationService.java`
  - Зависимости: `ApplicationRepository`, `VacancyRepository`, `UserRepository`, `NotificationService` (заглушка – только сохранение уведомлений в БД, без push).
  - Методы:
    - `ApplicationDto apply(int userId, int vacancyId)`
      - Проверка, что вакансия активна.
      - Проверка на повторный отклик (`findExisting`).
      - Проверка на спам: если `countByUserLastMinute(userId) >= 10`, выбрасывать исключение и логировать подозрительную активность.
      - Создание отклика со статусом PENDING.
      - **Создание уведомления для HR:** через `notificationService.create()` (сохраняется в БД).
      - Возврат DTO.
    - `List<ApplicationDto> getUserApplications(int userId)`
    - `List<ApplicationDto> getApplicationsForVacancy(int vacancyId, int hrUserId)` – проверка, что HR владеет вакансией.
    - `void updateStatus(int applicationId, String newStatus, int hrUserId)` – только HR может менять статус, при изменении создаётся уведомление соискателю.
- **Проверка:** `ApplicationServiceTest` с моками репозиториев и `NotificationService`.

### **6.5 Создание FavoriteService и ViewHistoryService**
- **Что делаем:** Простые сервисы для управления избранным и историей просмотров.
- **Файлы:**
  - `server/service/FavoriteService.java`
    - Методы: `void add(int userId, int vacancyId)`, `void remove(...)`, `List<VacancyDto> getFavorites(int userId)`, `boolean isFavorite(int userId, int vacancyId)`.
  - `server/service/ViewHistoryService.java`
    - Метод `void addView(int userId, int vacancyId)` – вызывается при каждом детальном просмотре вакансии.
    - Метод `List<VacancyDto> getRecentViews(int userId)` – возвращает последние N просмотренных вакансий.
- **Проверка:** Модульные тесты сервисов.

### **6.6 Создание ComplaintService**
- **Что делаем:** Сервис для подачи жалоб.
- **Файл:** `server/service/ComplaintService.java`

    - Проверка, что цель существует (вакансия или пользователь).
    - Сохранение жалобы в БД со статусом PENDING.
    - **Создание уведомления для администратора** (важное) – сохраняется в БД.
- **Проверка:** Тест с проверкой сохранения жалобы и уведомления.

### **6.7 Реализация серверных обработчиков команд для новых функций**
- **Что делаем:** Добавляем команды в `ClientHandler` (или через паттерн Command).
- **Команды:**
  - `APPLY` – принимает `vacancyId`, вызывает `applicationService.apply(userId, vacancyId)`.
  - `GET_MY_APPLICATIONS` – возвращает отклики текущего пользователя.
  - `GET_APPLICATIONS_FOR_VACANCY` – для HR, принимает `vacancyId`.
  - `UPDATE_APPLICATION_STATUS` – принимает `ApplicationStatusUpdateRequest`.
  - `ADD_FAVORITE` / `REMOVE_FAVORITE` – принимают `vacancyId`.
  - `GET_FAVORITES` – возвращает список избранного.
  - `ADD_VIEW` – вызывается клиентом при открытии деталей вакансии.
  - `CREATE_COMPLAINT` – принимает `ComplaintCreateRequest`.
- **Безопасность:** Проверка ролей (HR для управления статусами откликов, все авторизованные для откликов/жалоб/избранного).
- **Проверка:** Интеграционные тесты с отправкой команд через сокет.

### **6.10 Интеграционное тестирование сценариев этапа 6**
- **Что делаем:** Пишем тест на серверной стороне, эмулирующий полный цикл взаимодействия.
- **Сценарий:**
  1. Зарегистрировать соискателя и HR.
  2. HR создаёт вакансию.
  3. Соискатель просматривает детали вакансии (добавляется запись в историю просмотров).
  4. Соискатель добавляет вакансию в избранное.
  5. Соискатель откликается на вакансию.
  6. Проверяем, что в БД создан отклик со статусом PENDING.
  7. HR получает список откликов на свою вакансию – видит отклик.
  8. HR меняет статус на INVITED.
  9. Соискатель получает обновлённый статус в своих откликах.
  10. Соискатель подаёт жалобу на вакансию.
  11. Проверяем, что жалоба сохранена и администратор получит уведомление (проверяем запись в таблице notifications).
- **Проверка:** Все шаги выполняются без ошибок, данные в БД соответствуют ожиданиям.

## **Этап 7: Рекомендации (персонализированная лента, процент совпадения)**

### **7.1 Создание DTO для рекомендаций**
- **Что делаем:** Определяем структуру данных для вакансии с процентом совпадения.
- **Файл (в модуле `common`):**
  - `RecommendedVacancyDto.java`
    - Наследует `VacancyDto` или включает его + дополнительное поле `double matchPercent`.
- **Проверка:** Компиляция и сериализация.

### **7.2 Расширение VacancyRepository для получения вакансий с тегами**
- **Что делаем:** Добавляем метод, который возвращает все активные вакансии вместе с их тегами (или только ID тегов) для эффективной обработки рекомендаций.
- **Файл:** `server/repository/VacancyRepository.java`
  - Метод `List<VacancyWithTags> findAllActiveWithTags()` – возвращает список объектов, содержащих ID вакансии и коллекцию ID тегов.
  - **Вариант оптимизации:** Можно сделать запрос, который сразу вычисляет количество общих тегов, но для простоты реализуем в сервисе.
- **Проверка:** Тест для проверки корректности выборки.

### **7.3 Расширение UserRepository для получения тегов пользователя**
- **Что делаем:** Убедиться, что метод `findUserTags` работает эффективно.
- **Файл:** `server/repository/UserRepository.java`
  - Уже есть метод `List<Tag> findUserTags(int userId)`. Убедиться, что он возвращает только ID тегов или полные объекты. Для алгоритма рекомендаций достаточно ID.
- **Проверка:** Тест на получение тегов.

### **7.4 Создание RecommendationService с алгоритмом расчёта совпадения**
- **Что делаем:** Реализуем сервис, вычисляющий процент совпадения тегов пользователя и каждой активной вакансии.
- **Файл:** `server/service/RecommendationService.java`
  - Зависимости: `VacancyRepository`, `UserRepository`, `TagRepository`.
  - Метод `List<RecommendedVacancyDto> getRecommendations(int userId)`
    - Получаем `Set<Integer> userTagIds` из `userRepository.findUserTags(userId)`.
    - Если у пользователя нет тегов – возвращаем пустой список (или случайные вакансии, но по заданию – пусто).
    - Получаем `List<VacancyWithTags> vacancies` через `vacancyRepository.findAllActiveWithTags()`.
    - Для каждой вакансии:
      - `Set<Integer> vacancyTagIds` из данных.
      - `intersection = количество общих тегов`.
      - `union = userTagIds.size() + vacancyTagIds.size() - intersection`.
      - `matchPercent = (intersection * 2.0 / union) * 100` (формула Дайса, как в задании).
      - Если `matchPercent > 0`, добавляем в результат.
    - Сортируем результат по убыванию `matchPercent`.
    - Преобразуем в DTO, заполняя `matchPercent`.
  - **Оптимизация (опционально):** Можно кэшировать результат на 5 минут с помощью `Caffeine` или простого `Map` с временными метками.
- **Проверка:** `RecommendationServiceTest` с замоканными репозиториями, проверка вычисления процента на простых примерах.

### **7.5 Реализация серверного обработчика команды GET_RECOMMENDATIONS**
- **Что делаем:** Добавляем команду, доступную только авторизованным соискателям.
- **Команда:** `GET_RECOMMENDATIONS` (без параметров, userId из сессии).
- **Обработчик:** Вызывает `recommendationService.getRecommendations(userId)` и возвращает список `RecommendedVacancyDto`.
- **Проверка:** Интеграционный тест с созданием пользователя с тегами и нескольких вакансий с пересекающимися тегами, проверка порядка и процентов.

### **7.6 Клиентский сервис для получения рекомендаций**
- **Что делаем:** В клиенте создаём метод для запроса рекомендаций.
- **Файл:** `client/service/RecommendationClientService.java`
  - Метод `List<RecommendedVacancyDto> getRecommendations()`.
- **Проверка:** Ручной вызов с сервера, вывод результата в консоль.

### **7.7 Создание UI для отображения ленты рекомендаций**
- **Что делаем:** Добавляем новую вкладку «Рекомендованные» в главном окне соискателя.
- **Файлы:**
  - `client/src/main/resources/fxml/recommendations.fxml`
    - `TableView<RecommendedVacancyDto>` с колонками: заголовок, компания, город, зарплата, % совпадения (отображается как прогресс-бар или просто число).
    - При клике на вакансию открывать детали.
  - `client/controller/RecommendationsController.java`
    - При инициализации вызывает `RecommendationClientService.getRecommendations()` и заполняет таблицу.
    - Добавить кнопку «Обновить».
- **Проверка:** Запустить клиент, войти как соискатель с заполненными тегами, перейти на вкладку – отображаются вакансии с процентами, отсортированные по убыванию.

### **7.8 Подготовка к уведомлениям: заготовка в VacancyService**
- **Что делаем:** При создании новой вакансии HR'ом мы должны в будущем рассылать уведомления соискателям с совпадением ≥50%. На этом этапе только создаём заглушку или метод, который будет вызываться, но без фактической рассылки (чтобы не нарушать границы этапа).
- **Файл:** `server/service/VacancyService.java`
  - В методе `create` после сохранения вакансии добавить вызов `checkAndNotifyMatchingUsers(vacancyId)` (метод будет реализован в Этапе 9, сейчас он может быть пустым или просто логировать "Здесь будет рассылка уведомлений").
- **Проверка:** При создании вакансии в логах появляется запись о вызове заглушки.

### **7.9 Оптимизация алгоритма рекомендаций (опционально, но рекомендуется)**
- **Что делаем:** Добавляем предварительную фильтрацию: исключаем вакансии, у которых нет ни одного общего тега с пользователем, чтобы не вычислять процент для всех.
- **Реализация:** В `RecommendationService` при переборе вакансий сначала проверяем `!Collections.disjoint(userTagIds, vacancyTagIds)`, если нет пересечений – пропускаем.
- **Кэширование:** Внедряем простой `ConcurrentHashMap` с `userId` -> `(List<RecommendedVacancyDto>, timestamp)`. При запросе проверяем, не прошло ли 5 минут. Если кэш валиден – возвращаем его, иначе пересчитываем.
- **Проверка:** Тест на кэширование: два последовательных вызова `getRecommendations` с одним userId должны вызывать репозиторий только один раз.

### **7.10 Интеграционное тестирование сценария рекомендаций**
- **Что делаем:** На серверной стороне пишем тест, проверяющий полный цикл.
- **Сценарий:**
  1. Создать несколько тегов в БД (например, Java, Python, SQL).
  2. Зарегистрировать соискателя и назначить ему теги Java, SQL.
  3. HR создаёт вакансии:
     - Вакансия A: теги Java, Spring → совпадение с пользователем: 1 общий тег (Java). Пользователь: 2 тега, вакансия: 2 тега → union=3, intersection=1 → % = (1*2/3)*100 = 66.6%.
     - Вакансия B: теги Python, Django → общих 0 → 0%.
     - Вакансия C: теги Java, SQL, Docker → общих 2 (Java, SQL). Пользователь: 2 тега, вакансия: 3 тега → union=3, intersection=2 → % = (2*2/3)*100 = 133.3% (но по формуле Дайса максимум 100%, фактически (4/3)*100 ≈ 133.33% – возможно, нужно нормализовать, но в задании указано `(intersection * 2) / (userTags + vacancyTags) * 100`, что может давать >100%. Для реалистичности можно ограничить 100% или использовать `intersection / Math.max(userTags, vacancyTags) * 100`. В любом случае, проверим логику.)
  4. Запросить рекомендации для соискателя – проверить, что вакансии с ненулевым процентом возвращаются в порядке убывания процента, вакансия B отсутствует.
  5. Проверить работу кэша: изменить вакансию (добавить тег), подождать 5 минут или сбросить кэш, запросить снова – изменения учтены.
- **Проверка:** Все проверки проходят, проценты вычисляются корректно.
