## **Этап 1: Базовая инфраструктура, сетевое ядро, протокол, логирование**

### **1.1 Инициализация многомодульного Maven-проекта**
- **Что делаем:** Создан maven проект jobfinder на java 21. Создаём родительский `pom.xml` с модулями `common`, `server`, `client`.
- **Файлы:**
  - `/pom.xml` – родительский, определяет версию Java (21), кодировку, общие свойства.
  - `/common/pom.xml` – модуль для общих классов (Message, Response), зависимости: Jackson.
  - `/server/pom.xml` – модуль сервера, зависимости: `common`, Logback, JUnit (тесты).
  - `/client/pom.xml` – модуль клиента, зависимости: `common`, JavaFX, Logback.
- **Проверка:** Запуск `mvn clean compile` должен выполняться без ошибок.

### **1.2 Настройка логирования в модуле server**
- **Что делаем:** Добавляем зависимость Logback, создаём конфигурационный файл `logback.xml`.
- **Файлы:**
  - `/server/src/main/resources/logback.xml`:
    - Консольный appender для уровня INFO.
    - Файловый appender `logs/server.log` с ротацией (ежедневно или по размеру).
- **Код:** В классе `Server` (пока пустом) добавить `private static final Logger logger = LoggerFactory.getLogger(Server.class);`.
- **Проверка:** При запуске сервера в консоли должны появляться логи, и создаваться файл лога.

### **1.3 Создание общих классов сообщений в модуле common**
- **Что делаем:** Определяем структуру обмена данными между клиентом и сервером.
- **Файлы:**
  - `/common/src/main/java/com/jobapp/common/Message.java`
    - Поля: `private String type;` (например, `"REQUEST"`), `private String command;` (например, `"LOGIN"`), `private Object data;`
    - Конструкторы, геттеры/сеттеры, `toString()`.
  - `/common/src/main/java/com/jobapp/common/Response.java`
    - Поля: `private String status;` (`"OK"`, `"ERROR"`), `private String message;`, `private Object data;`
- **Зависимости:** В `common/pom.xml` – Jackson для сериализации (аннотации `@JsonCreator`, `@JsonProperty`).
- **Проверка:** Написать простой тест в `common` для проверки сериализации/десериализации JSON.

### **1.4 Реализация серверного сокета и пула потоков**
- **Что делаем:** Пишем класс `Server`, который открывает `ServerSocket` на заданном порту и для каждого подключения запускает `ClientHandler` в отдельном потоке из пула.
- **Файлы:**
  - `/server/src/main/java/com/jobapp/server/Server.java`
    - Поля: `private static final int PORT = 8081;`, `private ExecutorService threadPool;`
    - Метод `start()`: бесконечный цикл `serverSocket.accept()`, передача сокета в `new ClientHandler(socket)`, запуск через `threadPool.execute(handler)`.
    - Логирование старта и подключений.
  - `/server/src/main/java/com/jobapp/server/ClientHandler.java` (заглушка):
    - Реализует `Runnable`.
    - В `run()` получает `BufferedReader` и `PrintWriter` из сокета.
    - Читает строки (JSON), пока не получит `exit`.
    - Выводит в лог полученное сообщение и отправляет эхо-ответ.
- **Проверка:** Запустить сервер, через `telnet` или простой Java-клиент отправить JSON-строку, получить ответ.

### **1.5 Создание Dockerfile для сервера**
- **Что делаем:** Пишем `Dockerfile` для сборки образа сервера (используем multi-stage build для уменьшения размера).
- **Файлы:**
  - `/server/Dockerfile`
    - Stage 1 (build): `maven:3.9-eclipse-temurin-21` копирует исходники, запускает `mvn clean package` (только модуль server).
    - Stage 2 (runtime): `eclipse-temurin:21-jre-alpine`, копирует jar из stage 1, определяет точку входа `java -jar server.jar`.
- **Проверка:** Собрать образ командой `docker build -t jobapp-server .` из папки `server`.

### **1.6 Настройка docker-compose с PostgreSQL (пустая БД)**
- **Что делаем:** Создаём `docker-compose.yml` в корне проекта, определяем сервисы `postgres` и `server`.
- **Файлы:**
  - `/docker-compose.yml`
    - Сервис `postgres`: образ `postgres:15`, переменные окружения `POSTGRES_DB=jobdb`, `POSTGRES_USER=jobuser`, `POSTGRES_PASSWORD=secret`, volume для данных.
    - Сервис `server`: сборка из `./server/Dockerfile`, порты `8080:8080`, depends_on `postgres`, переменные окружения для подключения к БД.
- **Проверка:** `docker-compose up` – должны подняться оба контейнера, сервер пытается подключиться к БД (но таблиц ещё нет).

### **1.7 Базовая реализация клиентского NetworkService**
- **Что делаем:** В модуле `client` создаём класс для управления сокетным соединением.
- **Файлы:**
  - `/client/src/main/java/com/jobapp/client/NetworkService.java`
    - Метод `connect(String host, int port)` – создаёт сокет, `BufferedReader`, `PrintWriter`.
    - Метод `sendMessage(Message msg)` – сериализует в JSON и отправляет.
    - Метод `startListening(Consumer<Response> onResponse)` – запускает фоновый поток (`Task` JavaFX), читает строки, десериализует в `Response` и вызывает колбэк на UI потоке.
    - Обработка исключений и попытка переподключения (заглушка).
- **Проверка:** Запустить клиент, нажать кнопку, должно отправляться сообщение на сервер (логи сервера подтвердят).

### **1.8 Создание окна входа в клиенте (JavaFX)**
- **Что делаем:** Создаём FXML-разметку и контроллер для окна логина.
- **Файлы:**
  - `/client/src/main/resources/fxml/login.fxml`
    - `TextField` для логина, `PasswordField` для пароля, кнопки «Вход», «Регистрация».
  - `/client/src/main/java/com/jobapp/client/controller/LoginController.java`
    - Инжект `NetworkService`.
    - Метод `handleLogin()` – формирует `Message` с command="LOGIN", данными (логин, пароль), отправляет через `NetworkService`.
    - Пока ответ просто выводится в консоль или в `Label` на форме.
- **Проверка:** Запустить клиент, ввести любые данные, нажать «Вход», увидеть ответ сервера в логах.

### **1.9 Обработка команд на сервере: заглушка LOGIN и PING**
- **Что делаем:** В `ClientHandler` добавляем простейший диспетчер команд без бизнес-логики.
- **Код:**
  - Метод `processMessage(Message msg)`: switch по `command`.
  - `"PING"` → возвращает `Response` со статусом "OK", data = "PONG".
  - `"LOGIN"` → всегда возвращает `Response` со статусом "OK", message = "Login stub".
  - `"EXIT"` → закрывает соединение.
- **Логирование:** При получении любой команды записывать в лог: `logger.info("Received command: {} from {}", msg.getCommand(), socket.getInetAddress());`.
- **Проверка:** Через клиент отправить `LOGIN` – получить ответ "Login stub".

### **1.10 Финальная сборка и тестовый прогон всего окружения**
- **Что делаем:**
  1. Убедиться, что `docker-compose up` поднимает и БД, и сервер.
  2. Запустить клиентское приложение (пока не в контейнере) и убедиться, что оно подключается к серверу в контейнере (порт 8080 должен быть проброшен).
  3. Проверить, что сообщения корректно сериализуются/десериализуются (логи сервера и клиента показывают JSON).
  4. Убедиться, что файл логов сервера создаётся и содержит записи о подключениях.
- **Результат этапа:** Готовая инфраструктура, клиент и сервер обмениваются сообщениями, логи работают, всё упаковано в Docker.

## **Этап 2: База данных, репозитории, сущности (без бизнес-логики)**

### **2.1 Проектирование схемы БД в виде SQL-скрипта**
- **Что делаем:** Пишем `init.sql` со всеми таблицами, связями, индексами в соответствии с утверждённым списком.
- **Файлы:**
  - `/db/init.sql`
    - Таблицы: `users`, `companies`, `tags`, `vacancies`, `user_tags`, `vacancy_tags`, `applications`, `favorites`, `notifications`, `complaints`, `password_reset_tokens`, `block_history`.
    - Все поля, типы, PRIMARY KEY, FOREIGN KEY с ON DELETE RESTRICT / CASCADE (где уместно).
    - Индексы: `users(email)`, `vacancies(created_at)`, `applications(user_id, vacancy_id)`.
- **Проверка:** Скрипт должен выполняться без ошибок в PostgreSQL.

### **2.2 Интеграция скрипта инициализации в docker-compose**
- **Что делаем:** Настраиваем автоматическое создание схемы при старте контейнера PostgreSQL.
- **Файлы:**
  - `/docker-compose.yml`:
    - Для сервиса `postgres` добавить volume: `- ./db/init.sql:/docker-entrypoint-initdb.d/init.sql`
  - Перезапустить `docker-compose down -v && docker-compose up`.
- **Проверка:** Подключиться к БД через клиент (например, DBeaver) и убедиться, что все таблицы созданы.

### **2.3 Добавление зависимостей для работы с БД в модуль server**
- **Что делаем:** В `server/pom.xml` добавляем:
  - `org.postgresql:postgresql`
  - `com.zaxxer:HikariCP` (пул соединений)
  - (опционально) `org.slf4j:slf4j-api` уже есть с Logback.
- **Проверка:** `mvn dependency:tree` показывает новые зависимости.

### **2.4 Реализация конфигурации пула соединений HikariCP**
- **Что делаем:** Создаём класс `DatabaseConfig` для получения `DataSource`.
- **Файлы:**
  - `/server/src/main/java/com/jobapp/server/db/DatabaseConfig.java`
    - Статический метод `getDataSource()` возвращает `HikariDataSource`.
    - Параметры подключения читаются из переменных окружения (`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`) или из `application.properties`.
    - Настройки пула: максимальное количество соединений, таймауты.
- **Проверка:** В `main` сервера вызвать `getDataSource().getConnection()` и проверить, что соединение устанавливается (логи HikariCP).

### **2.5 Создание классов-сущностей (Entity)**
- **Что делаем:** Создаём POJO-классы, отражающие таблицы БД.
- **Файлы (пакет `server.model`):**
  - `User.java` (id, email, passwordHash, role, name, surname, city, phone, additionalInfo, isBlocked, blockedUntil, createdAt)
  - `Tag.java` (id, name, isActive)
  - `Company.java` (id, userId, companyName, website, description)
  - `Vacancy.java` (id, companyId, title, description, city, salaryMin, salaryMax, employmentType, isActive, createdAt, closedAt)
  - `Application.java` (id, vacancyId, userId, status, createdAt, updatedAt)
  - `Notification.java` (id, userId, type, title, content, link, isRead, createdAt)
  - `Complaint.java` (id, userId, targetType, targetId, reason, status, createdAt, resolvedBy, resolvedAt)
- Все классы содержат только поля, конструкторы, геттеры/сеттеры (можно Lombok для краткости).
- **Проверка:** Компиляция без ошибок.

### **2.6 Реализация UserRepository (JDBC)**
- **Что делаем:** Пишем репозиторий для работы с таблицей `users`.

      - `void delete(int id)` (или пометить удалённым)
    - Используем `JdbcTemplate` или чистый JDBC с `PreparedStatement`.
    - Пишем RowMapper для преобразования ResultSet в User.
- **Тесты:** Написать модульный тест `UserRepositoryTest` с использованием H2 in-memory БД (или Testcontainers).
- **Проверка:** Тесты проходят.

### **2.7 Реализация репозиториев для остальных основных сущностей**

## **Этап 3: Аутентификация, регистрация, роли, хеширование паролей**

### **3.1 Добавление зависимости BCrypt**
- **Что делаем:** В `server/pom.xml` добавляем библиотеку `org.mindrot:jbcrypt:0.4` (или `org.springframework.security:spring-security-crypto`).
- **Проверка:** `mvn clean compile` проходит.

### **3.2 Создание утилитного класса PasswordUtil**
- **Что делаем:** Инкапсулируем хеширование и проверку паролей.
- **Файлы:**
  - `/server/src/main/java/com/jobapp/server/util/PasswordUtil.java`
    - Статические методы: `String hash(String plainPassword)`, `boolean verify(String plainPassword, String hashed)`.
    - Используем `BCrypt.gensalt()` и `BCrypt.checkpw()`.
- **Проверка:** Написать простой тест `PasswordUtilTest`, проверяющий корректность хеширования и верификации.

### **3.3 Расширение UserRepository методами для аутентификации**
- **Что делаем:** Убедиться, что `findByEmail` возвращает пользователя с полем `passwordHash`.
- Добавить метод `boolean existsByEmail(String email)`.
- (Опционально) метод для обновления пароля: `updatePassword(int userId, String newPasswordHash)`.
- **Проверка:** Дополнить тесты репозитория.

### **3.4 Создание DTO для регистрации и логина**
- **Что делаем:** В модуле `common` (или `server.dto`) создаём классы для передачи данных.
- **Файлы:**
  - `common/src/main/java/com/jobapp/common/dto/RegisterRequest.java`:
    - Поля: email, password, role ("USER" или "HR"), name, surname (минимум).
  - `common/src/main/java/com/jobapp/common/dto/LoginRequest.java`:
    - Поля: email, password.
  - `common/src/main/java/com/jobapp/common/dto/AuthResponse.java`:
    - Поля: success, message, userId, role.
- **Проверка:** Сериализация/десериализация JSON работает.

### **3.5 Реализация сервиса AuthService**
- **Что делаем:** Класс, содержащий бизнес-логику регистрации и входа.
- **Файлы:**
  - `/server/src/main/java/com/jobapp/server/service/AuthService.java`
    - Зависимости: `UserRepository`, `PasswordUtil`.
    - Метод `register(RegisterRequest req)`:
      - Проверка, что email не занят (через `existsByEmail`).
      - Создание объекта `User` с ролью, хеширование пароля.
      - Сохранение через `userRepository.save()`.
      - Если роль HR, также создать запись в таблице `companies` с минимальными данными.
      - Возвращает `AuthResponse`.
    - Метод `login(LoginRequest req)`:
      - Поиск пользователя по email.
      - Если не найден или пароль неверен, возврат ошибки.
      - Проверка, не заблокирован ли пользователь (поле `isBlocked` и `blockedUntil`).
      - Возвращает `AuthResponse` с userId и ролью.
- **Логирование:** Записывать попытки входа (успешные и неудачные).
- **Проверка:** Написать юнит-тест `AuthServiceTest` с замоканным `UserRepository`.

### **3.6 Реализация SessionManager для отслеживания активных сессий**
- **Что делаем:** Храним соответствие userId -> `PrintWriter` (для отправки push-уведомлений).
- **Файлы:**
  - `/server/src/main/java/com/jobapp/server/service/SessionManager.java`
    - Потокобезопасная `ConcurrentHashMap<Integer, PrintWriter> activeSessions`.
    - Методы: `addSession(int userId, PrintWriter out)`, `removeSession(int userId)`, `PrintWriter getSession(int userId)`, `boolean isOnline(int userId)`.
    - При добавлении сессии логировать.
- **Проверка:** Пока не используется в полной мере, но будет необходимо для уведомлений.

### **3.7 Создание обработчиков команд LOGIN и REGISTER**
- **Что делаем:** В `ClientHandler` добавляем вызов `AuthService`.
- **Файлы:**
  - `/server/src/main/java/com/jobapp/server/handler/LoginCommand.java` (или встроенный switch)
    - Извлекает `LoginRequest` из `Message.data`.
    - Вызывает `authService.login()`.
    - При успехе: создаёт сессию через `sessionManager.addSession(userId, out)`.
    - Отправляет `Response` клиенту.
  - Аналогично `RegisterCommand`.
- **Важно:** Сессия привязывается к текущему `PrintWriter` обработчика.
- **Проверка:** Через клиент зарегистрировать нового пользователя, затем войти. Сервер должен вернуть корректный `AuthResponse`.

### **3.8 Обработка выхода (LOGOUT) и очистка сессии**
- **Что делаем:** Добавляем команду `LOGOUT`.
- **Код:**
  - В `processMessage` по команде `LOGOUT` вызываем `sessionManager.removeSession(userId)` (userId должен быть известен из контекста сессии, который мы ещё не храним в `ClientHandler` – нужно добавить поле `private Integer currentUserId`).
  - Закрывать соединение или оставлять открытым для возможности повторного входа? Лучше закрывать.
- **Проверка:** После логаута повторный вход должен работать.

### **3.9 Интеграция ролей в ответы сервера**
- **Что делаем:** Убедиться, что после успешного входа клиент получает роль пользователя, чтобы показать соответствующий интерфейс.
- **Модификация:** В `AuthResponse` есть поле `role`. Клиент после логина сохраняет её в статическом контексте (например, `AppContext.currentRole`).
- **Проверка:** В клиентском `LoginController` после успешного входа вывести сообщение с ролью и переключить сцену (пока пустую заглушку главного окна).

### **3.10 Написание интеграционного теста для сценария регистрация-вход**
- **Что делаем:** Создаём тестовый класс, который запускает сервер на случайном порту, подключается к нему сокетом и эмулирует клиентские запросы.
- **Используем:** JUnit 5, возможно, `ServerSocket` в `@BeforeAll`.
- **Сценарий:**
  1. Отправить `REGISTER` с новым email.
  2. Проверить ответ (успех).
  3. Отправить `LOGIN` с теми же данными.
  4. Проверить ответ (успех, получен userId и роль).
  5. Отправить `LOGOUT`.
- **Проверка:** Тест проходит, подтверждая, что весь этап реализован корректно.
