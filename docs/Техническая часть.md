Уведомления удобно реализовать через паттерн **Observer** (или **Listener**). Например, при создании отклика срабатывает событие, которое вызывает `NotificationService`, а тот уже рассылает уведомления через `SessionManager` (список активных сокетов) и сохраняет в БД.

### Дополнительные технические возможности (не функциональные, но важные)
- **Многопоточная обработка** – пул потоков на сервере для обработки запросов клиентов.
- **Сериализация/десериализация** – обмен данными в формате JSON (или Java serialization).
- **База данных** – PostgreSQL, нормализованная до 3НФ (не менее 5 связанных таблиц).
- **Docker** – контейнеризация сервера и базы данных для удобства развёртывания.
- **Логирование** – Log4j / java.util.logging для записи событий в файл.
- **Юнит-тестирование** – JUnit + Mockito для проверки бизнес-логики.
- **Сборка** – Maven или Gradle.
- **Графический интерфейс клиента** – JavaFX с современным дизайном (CSS, возможно JFoenix).

## Техническая реализация курсового проекта

Ниже представлен детальный план реализации, охватывающий архитектуру, технологии, ключевые механизмы и сложные моменты. Все решения соответствуют требованиям задания и вашим функциональным пожеланиям.

---

### 1. Общая архитектура

```
[Клиент (JavaFX)] <--TCP/IP (сокеты)--> [Сервер (Java SE)] <--> [БД (PostgreSQL)]
```

- **Сервер** – многопоточное консольное приложение, принимающее подключения от клиентов.
- **Клиент** – десктопное приложение на JavaFX, общается с сервером через сокеты.
- **БД** – PostgreSQL, развёрнутая в Docker-контейнере.
- **Сборка** – Maven/Gradle.
- **Логирование** – Logback (файловые логи + уведомление админа об ошибках).
- **Контейнеризация** – Docker для сервера и БД.

---

### 2. Серверная часть

#### 2.1. Сетевой уровень
- **ServerSocket** на фиксированном порту. Усчтановить леплой через фаст апи, файрфлайс и хайбернейт При подключении клиента создаётся новый поток из пула (`ExecutorService`).
- Для каждого клиента поддерживается постоянное соединение (сессия). Обмен сообщениями в формате JSON (библиотека `Jackson` или `Gson`).
- Протокол: клиент отправляет команду (например, `LOGIN`, `GET_VACANCIES`) с параметрами, сервер возвращает ответ (`статус + данные`). Для уведомлений сервер может инициировать отправку данных клиенту в любой момент (push).

#### 2.2. Обработка команд
- Паттерн **Command** или **Strategy**: каждое действие клиента инкапсулируется в отдельный класс (например, `LoginCommand`, `ApplyCommand`), который выполняется в потоке обработчика.
- Контроллер сессии (например, `ClientHandler`) читает JSON, определяет команду, вызывает соответствующий сервис и отправляет результат обратно.

#### 2.3. Бизнес-логика (сервисы)
- Сервисы реализуют всю логику, работают с репозиториями (DAO).
- Примеры сервисов:
  - `UserService` – регистрация, аутентификация, управление профилем.
  - `VacancyService` – CRUD вакансий, поиск, фильтрация.
  - `RecommendationService` – расчёт процента совпадения тегов.
  - `ApplicationService` – отклики, статусы.
  - `NotificationService` – создание и рассылка уведомлений.
  - `AnalyticsService` – формирование статистических данных.
  - `AdminService` – модерация, управление тегами.
  - `SecurityService` – хеширование паролей, проверка токенов.

#### 2.4. Работа с базой данных
- **JDBC** с пулом соединений (HikariCP) или **Hibernate** (JPA) для удобства.
- Сущности (Entity) соответствуют таблицам.
- DAO (репозитории) инкапсулируют запросы.
- Для сложных аналитических запросов можно использовать нативные SQL-запросы с агрегацией.

#### 2.5. Система уведомлений
- **Хранение:** таблица `notifications` (id, user_id, type, content, is_read, created_at, link).
- **Отправка:**
  - Сервер поддерживает карту активных сессий: `Map<Integer, PrintWriter>` (userId -> выходной поток сокета).
  - При возникновении события (новый отклик, новая вакансия) сервис вызывает `NotificationService.send(userId, notification)`.
  - Если пользователь онлайн – уведомление отправляется мгновенно через его сокет.
  - В любом случае уведомление сохраняется в БД.
  - При входе клиент запрашивает непрочитанные уведомления (синхронизация).
- **Техническая реализация:** для отправки JSON по сокету использовать тот же формат, но с тегом `"type": "notification"`. Клиент слушает входящие сообщения в отдельном потоке.

#### 2.6. Логирование
- **Logback** – конфигурация для вывода в файл и консоль.
- Уровни: INFO (основные действия пользователя), ERROR (исключения).
- Для логирования действий использовать АОП (Spring AOP, AspectJ) или ручные вызовы в сервисах.
- При критических ошибках отправлять уведомление администратору (через `NotificationService`).

#### 2.7. Безопасность
- **Пароли:** хешировать BCrypt (библиотека `jBCrypt` или `Spring Security Crypto`).
- **Аутентификация:** при успешном входе сервер создаёт сессию (хранит userId, роль) и привязывает к сокету.
- **Восстановление пароля:** генерация временного токена (UUID), сохранение в БД со сроком действия, отправка письма через SMTP (JavaMail). Клиент переходит по ссылке (имитация: отдельный endpoint на сервере) и вводит новый пароль.
- **Роли:** проверяются перед выполнением команд (например, `@RequiresRole` в команде).

#### 2.8. Обнаружение подозрительной активности
- Счётчики действий в памяти (например, `Map<Integer, List<Long>>` для userId -> временные метки последних откликов). Проверка: если больше 10 за минуту – блокировка.
- Альтернатива: запись действий в отдельную таблицу `audit_log` и периодический анализ (может быть избыточно для курсовой).
- Для простоты можно реализовать в сервисе `ApplicationService` при создании отклика: проверить количество откликов за последние 60 секунд, при превышении – отклонить отклик, занести в лог, уведомить админа.

#### 2.9. Восстановление соединения после разрыва
- Клиент при потере связи пытается переподключиться с экспоненциальной задержкой.
- При переподключении сервер может восстановить сессию, если клиент отправит сохранённый идентификатор сессии (например, userId + токен). Либо клиент заново логинится.

#### 2.10. Многопоточность и синхронизация
- Потокобезопасность коллекций (ConcurrentHashMap).
- Для общих ресурсов (счётчики, пулы) – синхронизация или атомарные классы.
- Доступ к БД через пул соединений (каждое обращение в отдельном потоке).

### 3. Клиентская часть (JavaFX)

#### 3.1. Структура
- MVC: `View` (FXML), `Controller`, `Model` (классы-обёртки данных).
- Основные экраны:
  - Окно входа/регистрации.
  - Главное окно с вкладками для разных ролей.
  - Профиль.
  - Страница вакансии.
  - Аналитика (графики).
- Для построения графиков использовать библиотеку **JFreeChart** или встроенные средства JavaFX (`LineChart`, `BarChart`).

#### 3.2. Сетевое взаимодействие
- Отдельный поток `NetworkListener`, который читает входящие сообщения от сервера.
- При получении уведомления – показывать всплывающее сообщение (Toast) и обновлять счётчик.
- Отправка команд: блокирующий вызов с ожиданием ответа (синхронно) через `CompletableFuture` или очередь сообщений. Для асинхронности – использовать `Task` или `Service`.

#### 3.3. Обработка уведомлений
- При запуске клиент запрашивает `GET_UNREAD_NOTIFICATIONS`.
- В отдельном потоке слушает push-уведомления. При получении – добавляет в локальный список и обновляет UI.
- Клиент отмечает уведомление прочитанным при клике.

#### 3.4. Визуализация аналитики
- Клиент запрашивает данные с сервера в виде JSON (например, списки точек для графика).
- Контроллер заполняет график.
- Для удобства можно использовать **JasperReports** или генерировать PNG, но это избыточно.

#### 3.5. Локализация и дизайн
- Применить CSS для стилизации JavaFX.
- Можно использовать **JFoenix** для Material Design компонентов.

### 5. Реализация ключевых фич

#### 5.1. Система рекомендаций
- При запросе `GET_RECOMMENDATIONS` сервер получает теги пользователя, загружает все активные вакансии с тегами.
- Для каждой вакансии вычисляет `совпадение = (количество общих тегов * 2) / (теги_пользователя + теги_вакансии) * 100%`.
- Сортирует по убыванию, возвращает список.
- Оптимизация: предварительная фильтрация вакансий, содержащих хотя бы один из тегов пользователя.

#### 5.2. Фильтрация и поиск
- Серверный эндпоинт `FILTER_VACANCIES` принимает параметры (city, salary_from, salary_to, employment_type, tag_ids, keyword). Строит динамический SQL-запрос (используя `CriteriaBuilder` в Hibernate или ручное построение через StringBuilder).

#### 5.3. Статистика и аналитика
- Аналитические запросы выполняются на сервере через SQL с агрегатными функциями.
- Пример для графика зарплат: `SELECT DATE(created_at) as date, AVG(salary_min + salary_max)/2 FROM vacancies WHERE ... GROUP BY date`.
- Для трендов навыков: `SELECT t.name, COUNT(*) FROM vacancy_tags vt JOIN tags t ON vt.tag_id = t.id WHERE ... GROUP BY t.name ORDER BY count DESC`.
- Данные возвращаются в JSON, клиент строит график.

#### 5.4. Уведомления
- При создании отклика: `NotificationService.notifyHR(vacancy.getCompany().getUserId(), "Новый отклик", "На вакансию ...", "/vacancy/"+vacancyId)`.
- При создании вакансии: проверить всех соискателей, у которых процент совпадения ≥50%, и отправить им уведомление (можно асинхронно, чтобы не задерживать ответ).

#### 5.5. Жалобы
- Таблица `complaints`. При отправке жалобы админу приходит уведомление (важное). Админ просматривает список жалоб и принимает решение: заблокировать вакансию/пользователя или отклонить.

#### 5.6. Блокировка пользователя
- Поле `is_blocked` и `blocked_until`. При аутентификации проверяется.
- Блокировка может быть временной (дата окончания) или постоянной (null).
- При блокировке разрывается текущая сессия (закрыть сокет).

#### 5.7. Создание первого администратора
- При старте сервера проверять, есть ли хотя бы один администратор в БД. Если нет – создать учётную запись с фиксированным логином/паролем (например, admin/admin) или запросить при первом запуске.

#### 5.8. Восстановление пароля
- Сервер генерирует токен, сохраняет в таблице `password_reset_tokens` (id, user_id, token, expires_at).
- Отправляет письмо на email с ссылкой вида `http://localhost:8080/reset?token=...` (можно эмулировать простым GET-запросом, который открывает окно ввода нового пароля на клиенте). Клиент должен иметь возможность ввести новый пароль и отправить команду `RESET_PASSWORD` с токеном.
