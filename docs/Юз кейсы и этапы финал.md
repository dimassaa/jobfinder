## Этап 1: Базовая инфраструктура, сетевое ядро, протокол, логирование

**Цель:** Создать каркас сервера и клиента, настроить сетевое взаимодействие и логгирование.

- Создать Maven/Gradle проект с модулями `server`, `client`, `common`.
- Настроить зависимости: Jackson (JSON), Logback, Lombok (опционально), JavaFX (для клиента).
- В `common`: определить класс `Message` (type, command, data) и `Response` (status, data, error).
- **Сервер:**
  - Класс `Server` с `ServerSocket`, пул потоков (`Executors.newCachedThreadPool()`).
  - Обработчик клиента `ClientHandler` (Runnable), читает JSON из `BufferedReader`, парсит, пока не получит `exit`.
  - Заглушка обработки команд: `echo` (возвращает полученное), `ping`.
  - Логирование через Logback (файл `app.log`, уровень INFO).
- **Клиент:**
  - JavaFX приложение с окном входа (логин, пароль, кнопки «Вход», «Регистрация»).
  - Класс `NetworkService` (сокет, отправка сообщений, слушатель ответов в отдельном потоке).
  - При нажатии «Вход» клиент отправляет команду `LOGIN` (с паролем в открытом виде пока), получает ответ – выводит в консоль.
- **Docker:** `docker-compose.yml` с сервисом `postgres` (пустая, без схемы пока), `server` собирается из Dockerfile.

**Результат:** Сервер принимает подключения, логирует действия. Клиент подключается, отправляет `LOGIN` (заглушка), получает ответ. Всё запускается через Docker Compose.

## Этап 3: Аутентификация, регистрация, роли, хеширование паролей

**Цель:** Полноценная аутентификация, регистрация пользователей с ролями, хеширование BCrypt.

- Дополнить `UserRepository` методом `findByLogin` (логин уникален).
- **Сервис `AuthService`:**
  - `register(RegisterDto)` – проверяет уникальность email/логина, хеширует пароль, сохраняет пользователя с ролью (USER/HR).
  - `login(login, password)` – ищет пользователя, проверяет пароль через `BCrypt.checkpw()`, возвращает объект `Session` (userId, role).
- **Обработчики команд:** реализовать команды `REGISTER`, `LOGIN`. Ответ содержит сессионный токен (например, UUID) или просто признак успеха.
- **Сервер:** добавить `SessionManager` – хранит активные сессии (userId -> PrintWriter и роль). При `LOGIN` создаётся сессия, при `LOGOUT` удаляется.
- **Клиент:** после успешного логина сохраняет сессию, переключает интерфейс на главное окно (пока пустое). Реализовать окно регистрации с выбором роли и полями.
- **Логирование:** логировать неудачные попытки входа.

**Результат:** Можно зарегистрировать соискателя, HR, войти под ними, сервер различает роли. Пароли хранятся хешированными.

## Этап 7: Рекомендации (персонализированная лента, процент совпадения)

**Цель:** Реализовать алгоритм ранжирования вакансий по тегам пользователя, выдать ленту «Рекомендованные».

- **Сервер:**
  - `RecommendationService.getRecommendations(userId)`:
    - Получить теги пользователя.
    - Получить все активные вакансии с их тегами.
    - Для каждой вакансии вычислить:
      `intersection = количество общих тегов`
      `union = теги_пользователя.size() + теги_вакансии.size() - intersection`
      `matchPercent = (intersection * 2.0 / union) * 100` (или упрощённо: `(intersection / tagsUserCount) * 100`, если вакансия должна покрывать навыки пользователя).
    - Отфильтровать вакансии с `matchPercent > 0`, отсортировать по убыванию.
    - Добавить в DTO поле `matchPercent`.
  - Кэширование результатов (опционально, на 5 минут).
- **Обработчик:** `GET_RECOMMENDATIONS`.
- **Клиент:**
  - Добавить вкладку «Рекомендованные» (первая при входе).
  - Отображать процент совпадения рядом с вакансией (например, «90% совпадение»).
  - При получении уведомлений о новых вакансиях с ≥50% – показывать всплывашку.
- **Уведомления:** при создании новой вакансии `VacancyService` вызывает `NotificationService.checkAndNotifyUsers(vacancy)`, который вычисляет для всех соискателей совпадение и если ≥50% – создаёт уведомление и отправляет онлайн-пользователям.

**Результат:** Соискатель видит релевантные вакансии с процентом совпадения. Рекомендации работают в реальном времени.

  - Для админа: общая статистика, активность по дням, топ-теги.
- **Фильтр по периодам** (неделя, месяц, год) – передавать в запросе.

**Результат:** Пользователи видят красивые графики и аналитику в реальном времени.

## Этап 9: Система уведомлений (полноценная: хранение, push, история, настройки)

**Цель:** Реализовать сохранение уведомлений в БД, push через открытый сокет, окно истории, отметку прочитанных, базовые настройки.

- **Сервер:**
  - Таблица `notifications` уже есть. `NotificationService.save(notification)` сохраняет.
  - `NotificationService.sendToUser(userId, notification)` – если пользователь онлайн (сессия есть), отправляет JSON с типом `NOTIFICATION` через его `PrintWriter`. В любом случае сохраняет.
  - При подключении клиента отправлять все непрочитанные уведомления.
  - Команды: `GET_NOTIFICATIONS`, `MARK_NOTIFICATION_READ`, `DELETE_NOTIFICATION`.
- **Клиент:**
  - Отдельный поток читает входящие сообщения от сервера. При получении `NOTIFICATION`:
    - Показывать всплывающее уведомление (Toast или системный трей).
    - Добавить в локальный список и обновить счётчик на иконке колокольчика.
  - Окно «Уведомления» со списком, возможностью отметить прочитанное.
  - Настройки уведомлений (опционально) – какие типы получать.
- **События, генерирующие уведомления:**
  - Новая вакансия с совпадением ≥50% → соискателю.
  - Новый отклик → HR.
  - Изменение статуса отклика → соискателю.
  - Жалоба → админу.
  - Приветственное, напоминание о профиле (по расписанию, можно через `ScheduledExecutorService` раз в день).

**Результат:** Работает полноценная система уведомлений в реальном времени.

  - Добавить healthcheck для сервера.
- **Тестирование:** написать несколько интеграционных тестов (JUnit + Testcontainers).
- **Документация:** подготовить `README.md` с инструкцией по запуску через Docker Compose.

#### **Явное использование паттерна Command (уточнение шага 1.9/3.7)**

- **Что делаем:** Вместо switch-case в `ClientHandler` создаём интерфейс `Command` и Map команд.
    
- **Файлы:**
    
    - **`server/command/Command.java`**
        
        java
        
        public interface Command {
            Response execute(Message message, ClientHandler context);
            String getName();
        }
        
    - **`server/command/LoginCommand.java`**, **`server/command/RegisterCommand.java`** и т.д.
        
    - **`server/ClientHandler.java`**:
        
        - При инициализации сервера регистрируются все команды в `Map<String, Command>`.
            
        - В `processMessage()`: `Command cmd = commands.get(message.getCommand()); if (cmd != null) { Response resp = cmd.execute(message, this); }`
            
- **Проверка:** Структура кода соответствует паттерну Command, добавление новой команды сводится к созданию класса и регистрации.
    

#### **Проверка прав доступа при просмотре профиля другого пользователя (шаг 4.6)**

- **Что делаем:** Модифицируем команду `GET_PROFILE` для поддержки параметра `targetUserId`. Если указан, проверяем, что запрашивающий — HR и что целевой пользователь откликался на вакансию этого HR.
    
- **Изменения:**
    
    - **`server/handler/GetProfileCommand.java`**
        
        - Если `targetUserId != null` и не равен `sessionUserId`:
            
            - Проверить роль (должна быть HR).
                
            - Проверить через `ApplicationRepository`, есть ли отклик от `targetUserId` на любую вакансию компании HR.
                
            - Если нет — вернуть ошибку доступа.
                
    - **Клиент:** При просмотре профиля соискателя из списка откликов передавать `targetUserId`.
        
- **Проверка:** HR пытается просмотреть профиль случайного соискателя (не откликавшегося) — получает ошибку. Профиль откликнувшегося открывается.
