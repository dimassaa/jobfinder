## Этап 8: Аналитика (графики, статистика для соискателя, HR, админа)

### 8.1 Создание DTO для аналитических данных
- **Что делаем:** Определяем структуры для передачи агрегированных данных на клиент.
- **Файлы (в модуле `common`):**
  - `ChartDataPointDto.java` – точка графика: `String label`, `double value`.
  - `SalaryStatsDto.java` – список точек `List<ChartDataPointDto>`, возможно `String period`, `double average`.
  - `TopTagsDto.java` – список `TagUsageDto` (id, name, count).
  - `GeoDistributionDto.java` – список `CityCountDto` (city, count, avgSalary).
  - `ConversionStatsDto.java` – просмотры, отклики, приглашения, процент конверсии.
  - `SystemStatsDto.java` – общие числа: пользователей (по ролям), вакансий, откликов.
- **Проверка:** Компиляция и JSON-сериализация.

### 8.2 Расширение репозиториев аналитическими методами (JDBC/SQL)
- **Что делаем:** Добавляем в существующие репозитории (или создаём отдельный `AnalyticsRepository`) методы для агрегации.
- **Файл:** `server/repository/AnalyticsRepository.java` (или методы в существующих)
  - Методы:
    - `List<ChartDataPointDto> getSalaryStatsByUserTags(int userId, int days)`
      - SQL: `SELECT DATE(v.created_at) as date, AVG((v.salary_min + v.salary_max)/2) as avg_salary FROM vacancies v JOIN vacancy_tags vt ON v.id = vt.vacancy_id WHERE vt.tag_id IN (SELECT tag_id FROM user_tags WHERE user_id = ?) AND v.created_at >= NOW() - INTERVAL '? days' GROUP BY date ORDER BY date`
    - `List<TagUsageDto> getTopTags(int days, int limit)`
      - SQL: `SELECT t.id, t.name, COUNT(vt.vacancy_id) as count FROM vacancy_tags vt JOIN tags t ON vt.tag_id = t.id JOIN vacancies v ON vt.vacancy_id = v.id WHERE v.created_at >= NOW() - INTERVAL '? days' GROUP BY t.id, t.name ORDER BY count DESC LIMIT ?`
    - `List<CityCountDto> getGeoDistribution(String entityType, int days)`
      - Для вакансий: `SELECT city, COUNT(*) as count, AVG((salary_min+salary_max)/2) as avg_salary FROM vacancies WHERE created_at >= NOW() - INTERVAL '? days' GROUP BY city`
      - Для соискателей: `SELECT city, COUNT(*) as count FROM users WHERE role = 'USER' AND created_at >= NOW() - INTERVAL '? days' GROUP BY city`
    - `ConversionStatsDto getVacancyConversion(int vacancyId)`
      - Три отдельных COUNT: просмотры (`view_history`), отклики (`applications`), приглашения (`applications WHERE status IN ('INVITED','ACCEPTED')`)
    - `SystemStatsDto getSystemStats()`
      - COUNT по ролям, COUNT активных вакансий, COUNT откликов за всё время.
- **Проверка:** Написать тесты для каждого аналитического метода с известным набором данных.

### 8.3 Создание AnalyticsService с методами для каждой роли
- **Что делаем:** Сервис, который вызывает репозиторий и готовит данные в формате DTO.
- **Файл:** `server/service/AnalyticsService.java`
  - Методы (каждый возвращает соответствующий DTO):
    - `getSalaryStatsForUser(int userId, int periodDays)`
    - `getTopTags(int periodDays, int limit)`
    - `getGeoDistributionForVacancies(int periodDays)`
    - `getGeoDistributionForApplicants(int periodDays)`
    - `getVacancyConversion(int vacancyId, int hrUserId)` – проверка прав.
    - `getSalaryComparisonForTags(List<Integer> tagIds)` – средняя зарплата по вакансиям с указанными тегами.
    - `getSystemStats()`
    - `getActivityTimeline(int days)` – регистрации и вакансии по дням.
- **Проверка:** `AnalyticsServiceTest` с замоканным `AnalyticsRepository`.

#### **9.3а Реализация фоновой задачи напоминания о незаполненном профиле**

- **Что делаем:** Создаём `ScheduledExecutorService` на сервере, который раз в день проверяет пользователей, зарегистрированных более суток назад, у которых не заполнены обязательные поля (город, теги), и отправляет уведомление.
    
- **Файлы:**
    
    - **`server/service/ProfileReminderTask.java`**
        
        - Реализует `Runnable`.
            
        - Зависимости: `UserRepository`, `NotificationService`.
            
        - Логика: выбрать пользователей, где `created_at < NOW() - INTERVAL '1 day'` и (city IS NULL OR не имеет тегов).
            
        - Для каждого отправить уведомление с типом `PROFILE_REMINDER`.
            
    - **`server/Server.java`** (в методе `start()`)
        
        - Запустить задачу с фиксированной периодичностью 24 часа:
            
            java
            
            ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor();
            scheduler.scheduleAtFixedRate(new ProfileReminderTask(...), 1, 24, TimeUnit.HOURS);
            
- **Проверка:** Искусственно создать пользователя без города и тегов, изменить дату регистрации на вчера, дождаться выполнения задачи (или вызвать вручную), убедиться, что уведомление сохранено в БД.
    

#### **9.3б Интеграция Logback с уведомлениями администратора о критических ошибках**

- **Что делаем:** Создаём кастомный Logback `Appender`, который при записи события уровня `ERROR` вызывает `NotificationService` для отправки уведомления админам.
    
- **Файлы:**
    
    - **`server/src/main/java/com/jobapp/server/logging/NotificationAppender.java`**
        
        - Наследует `ch.qos.logback.core.AppenderBase<ILoggingEvent>`.
            
        - В методе `append()` получает `NotificationService` через статический контекст (например, `ApplicationContext.getNotificationService()`).
            
        - Отправляет уведомление всем администраторам.
            
    - **`server/src/main/resources/logback.xml`**
        
        - Добавить `<appender name="NOTIFICATION" class="com.jobapp.server.logging.NotificationAppender"/>`
            
        - Добавить `<root level="INFO"> <appender-ref ref="NOTIFICATION"/> </root>` с фильтром по уровню ERROR.
            
- **Проверка:** Спровоцировать ошибку на сервере (например, неверный JSON), убедиться, что администратор получает push-уведомление (если онлайн) и запись в таблице `notifications`.

### 8.4 Реализация серверных обработчиков аналитических команд
- **Что делаем:** Добавляем команды для каждого типа аналитики.
- **Команды:**
  - `GET_SALARY_STATS` (параметры: periodDays, userId из сессии) → только соискатель.
  - `GET_TOP_TAGS` (periodDays, limit)
  - `GET_GEO_STATS` (type: VACANCY/APPLICANT, periodDays)
  - `GET_CONVERSION` (vacancyId) → только HR для своей вакансии.
  - `GET_SALARY_COMPARISON` (tagIds) → HR.
  - `GET_SYSTEM_STATS` → админ.
  - `GET_ACTIVITY_TIMELINE` (days) → админ.
- **Безопасность:** Проверка ролей.
- **Проверка:** Интеграционные тесты с запросами и проверкой структуры JSON.

### 8.5 Клиентские сервисы для аналитики
- **Что делаем:** В клиенте создаём класс-обёртку.
- **Файл:** `client/service/AnalyticsClientService.java`
  - Методы для каждой команды, возвращают `CompletableFuture` или блокирующие вызовы (в фоновом потоке).
- **Проверка:** Ручное тестирование вызовов с выводом в консоль.

### 8.6 Подготовка UI для отображения графиков (JavaFX Charts)
- **Что делаем:** Добавляем в клиент вкладку «Аналитика» с переключателями ролей и периодами.
- **Файлы:**
  - `client/src/main/resources/fxml/analytics.fxml`
    - `TabPane` с вкладками: «Зарплаты», «Тренды навыков», «География», «Конверсия» (для HR), «Общая статистика» (для админа).
    - На каждой вкладке: `LineChart`/`BarChart`/`PieChart`, `ComboBox` для выбора периода (неделя, месяц, год).
  - `client/controller/AnalyticsController.java`
    - При инициализации определяет роль пользователя и показывает/скрывает вкладки.
    - Загружает данные через `AnalyticsClientService` и заполняет графики.
- **Проверка:** Запустить клиент, войти как соискатель, перейти в аналитику, увидеть заглушки графиков (нет данных) или реальные данные, если есть.

### 8.7 Реализация графиков для соискателя
- **Что делаем:** Наполняем вкладки данными для соискателя.
- **Действия:**
  - «Зарплаты»: `LineChart<String, Number>` (ось X – даты, Y – средняя зарплата). Данные из `GET_SALARY_STATS`.
  - «Тренды навыков»: `BarChart<String, Number>` (теги по убыванию частоты). Данные из `GET_TOP_TAGS`.
  - «Геоаналитика»: `BarChart` распределения вакансий по городам. Данные из `GET_GEO_STATS` (type=VACANCY).
- **Проверка:** После добавления тестовых данных в БД графики отображаются корректно.

### 8.8 Реализация графиков для HR
- **Что делаем:** Дополняем вкладки специфическими для HR данными.
- **Действия:**
  - «Конверсия»: отображение воронки (можно `BarChart` с тремя столбцами: просмотры, отклики, приглашения). Данные из `GET_CONVERSION`.
  - «Сравнение зарплат»: отображение средней зарплаты по выбранным тегам и сравнение с рыночной (данные из `GET_SALARY_COMPARISON`).
  - «Геоаналитика»: распределение соискателей по городам (`GET_GEO_STATS`, type=APPLICANT).
- **Проверка:** HR видит аналитику по своим вакансиям.

### 8.9 Реализация графиков для администратора
- **Что делаем:** Добавляем вкладки только для админа.
- **Действия:**
  - «Общая статистика»: `PieChart` по ролям пользователей, `BarChart` по дням активности (регистрации/вакансии).
  - «Топ-10 тегов» и «Геоаналитика» аналогичны соискателю, но по всей системе.
- **Проверка:** Админ видит агрегированные данные по системе.

### 8.10 Интеграционное тестирование аналитического модуля
- **Что делаем:** На сервере пишем тест, проверяющий корректность агрегаций.
- **Сценарий:**
  1. Создать тестовые данные: несколько пользователей, вакансии с разными датами, городами, зарплатами, тегами.
  2. Вызвать каждый аналитический метод и сравнить результат с ожидаемыми числами, рассчитанными вручную.
  3. Проверить фильтрацию по датам (период).
- **Проверка:** Все тесты проходят.

## Этап 9: Система уведомлений (полноценная: хранение, push, история, настройки)

  - Существующие: `save`, `findUnreadByUserId`.

    - `int countUnread(int userId)`
- **Проверка:** Тесты для каждого метода.

### 9.2 Расширение NotificationService для работы с push-уведомлениями
- **Что делаем:** Добавляем методы для отправки уведомлений онлайн-пользователям и сохранения в БД.
- **Файл:** `server/service/NotificationService.java`
  - Зависимости: `NotificationRepository`, `SessionManager`.
  - Методы:
    - `void sendToUser(int userId, NotificationDto notification)` – сохраняет в БД, затем вызывает `sendPush(userId, notification)`.
    - `void sendPush(int userId, NotificationDto notification)` – проверяет через `SessionManager.isOnline(userId)`, получает `PrintWriter`, отправляет JSON-сообщение с типом `"NOTIFICATION"`.
    - `List<NotificationDto> getUserNotifications(int userId, boolean unreadOnly, int limit, int offset)`
    - `void markAsRead(int notificationId, int userId)` – проверка принадлежности.
    - `void deleteNotification(int notificationId, int userId)`
  - **Важно:** При отправке push нужно обернуть в синхронизацию по `PrintWriter`, чтобы избежать одновременной записи.
- **Проверка:** `NotificationServiceTest` с моком `SessionManager` и репозитория.

### 9.3 Интеграция уведомлений в бизнес-события (триггеры)
- **Что делаем:** Вставляем вызовы `NotificationService` в соответствующие сервисы (которые уже частично созданы в этапе 6-7, но теперь с реальной отправкой push).
- **Файлы и изменения:**
  - **ApplicationService.apply()** – после создания отклика: `notificationService.sendToUser(hrUserId, new NotificationDto(NEW_APPLICATION, ...))`.
  - **ApplicationService.updateStatus()** – после смены статуса: `notificationService.sendToUser(applicantUserId, ...)`.
  - **VacancyService.create()** – после создания вакансии: вызвать метод `notifyMatchingUsers(vacancy)`.
    - Реализовать приватный метод в `VacancyService` или `RecommendationService`, который получает всех соискателей с процентом совпадения ≥50% и для каждого вызывает `notificationService.sendToUser(...)`.
    - Для производительности можно делать асинхронно (через `CompletableFuture.runAsync`), но на этом этапе делаем синхронно в рамках пула потоков сервера.
  - **ComplaintService.create()** – отправить уведомление всем админам (получить список админов из `UserRepository`).
- **Проверка:** При создании вакансии HR'ом проверяем, что в БД созданы уведомления для подходящих соискателей, и если они онлайн – в логах клиента появляется push.

### 9.6 Реализация фонового слушателя уведомлений в клиенте
- **Что делаем:** Модифицируем `NetworkService` или создаём отдельный `NotificationListener`, который в бесконечном цикле читает входящие сообщения и при получении типа `"NOTIFICATION"` вызывает колбэк.
- **Файл:** `client/service/NetworkService.java` (или новый класс)
  - Уже есть метод `startListening(Consumer<Response> onResponse)`. Его нужно расширить, чтобы он различал `Response` и `Message` (с типом NOTIFICATION). В текущем протоколе мы использовали `Response` для ответов на команды. Для push-уведомлений можно использовать тот же класс `Message` с полем `type="NOTIFICATION"`. Тогда в потоке чтения проверяем JSON: если есть поле `type` со значением `"NOTIFICATION"`, десериализуем в `NotificationDto` и передаём в UI колбэк.
- **Проверка:** Отправить тестовое уведомление с сервера, убедиться, что клиент его получает и выводит в консоль.

  - При открытии списка уведомлений и отметке прочитанным – обновлять счётчик.
- **Проверка:** Получить уведомление – счётчик увеличился.

### 9.10 Интеграционное тестирование всей системы уведомлений
- **Что делаем:** Пишем тест на серверной стороне, эмулирующий несколько клиентов и проверяющий доставку.
- **Сценарий:**
  1. Запустить сервер.
  2. Подключить два клиента (соискатель и HR) в отдельных потоках теста.
  3. HR создаёт вакансию с тегами, совпадающими с соискателем.
  4. Проверить, что соискатель получил push-уведомление (через чтение из сокета) и что уведомление сохранилось в БД.
  5. Соискатель откликается на вакансию.
  6. Проверить, что HR получил уведомление о новом отклике.
  7. HR меняет статус отклика.
  8. Проверить, что соискатель получил уведомление об изменении статуса.
  9. Проверить работу команд `GET_NOTIFICATIONS`, `MARK_READ`.
- **Использовать:** Java-клиенты в тесте, работающие с реальными сокетами.
- **Проверка:** Все шаги выполняются, уведомления доставляются мгновенно (если клиент онлайн) и сохраняются в БД.
